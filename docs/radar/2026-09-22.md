# Barrido de repos — 22-09-2026

Ocho proyectos del radar, analizados por cuatro sub-agentes en paralelo y
cruzados contra lo que Faustus ya tiene. Dos ideas se aceptan, dos mejoran algo
existente, tres se descartan. Todas las cifras de terceros que se citan abajo
son las que ellos mismos publican; donde no hay verificación independiente, se
dice.

## Aceptado

### 1. Decisión tipada en vez de texto libre → OBJ-27

Tesis compartida por dos proyectos del lote: cuando la salida real es *elegir
una opción de una lista cerrada*, dejar que un modelo grande escriba texto
libre es caro y alucinable. No es una idea nueva — es decodificación
restringida con nombre comercial — pero el diagnóstico aplica: Faustus usa el
27B para intención, enrutado, selección de herramienta y navegador.

De los dos proyectos que la venden:

- Uno tiene el harness con licencia permisiva pero **el motor de decisión es una
  API de pago cerrada**: sin clave no hay cerebro. Inútil para una instalación
  local. Lo aprovechable es su arquitectura, no su código: construir una tabla
  de elementos del DOM y ofrecer al modelo **solo las operaciones válidas para
  cada elemento concreto**, con un guard que detecte si la página cambió entre
  la captura y la acción. Eso se replica con el control de navegador que ya hay.
- El otro es Apache 2.0 con pesos descargables (encoder no autorregresivo de
  322-421M, del orden de 33 ms por decisión). Honesto sobre sus límites:
  degrada por encima de ~50 opciones y está cerca del azar fuera de dominio sin
  ajuste fino. Su comparativa contra el primero es autopublicada y cita una
  cifra sacada del marketing del rival: comparación de parte interesada contra
  parte interesada.

**Conclusión:** la idea se adopta, los proyectos no. Fase 1 con gramáticas
sobre el modelo ya cargado; fase 2 con un encoder propio solo si la medición lo
justifica.

### 2. Refinamiento propuesto tras cada tarea → OBJ-28

El proyecto de origen formaliza el estado del harness como (prompt,
sub-agentes, skills, memoria) y expone un comando que, al acabar una tarea, lee
la trayectoria y aplica el edit CRUD mínimo, con deshacer por identificador y
prompt base inmutable.

**El titular del proyecto no se sostiene** (ver abajo), pero el patrón sí, y
además es exactamente el coaching manual que se viene haciendo a mano después
de cada sesión larga. Faustus ya tiene la mitad: el pase de sueño de skills
propone revisiones que el usuario aprueba.

## Mejora algo que ya existe

### 3. Omisión recuperable en el contexto → OBJ-29

De un proyecto de compresión de contexto. Lo aprovechable no es su modelo
entrenado sino el patrón: comprimir de forma **reversible**, guardando el
original local con un identificador corto en el prompt y una herramienta que lo
recupera si el modelo lo pide. Más las heurísticas deterministas por tipo de
contenido (poda de JSON, colapso de bloques repetidos) antes de tocar nada con
un modelo.

A favor del proyecto: su script de comparación es reproducible, con semilla
fija y tokenización real, y su cabecera critica explícitamente las cifras no
verificables del sector. Es de lo más honesto del lote. En contra: la
compresión es con pérdida, y reescribir el contexto de forma distinta cada
turno es estructuralmente hostil al caché de prefijo de los backends locales —
un problema que esta casa ya conoce de la línea de idioma del prompt.

### 4. Generación declarativa de herramientas desde una especificación de API

De un proyecto de conectores. El catálogo (varios cientos de adaptadores) está
fuertemente sesgado a software empresarial de un solo mercado y es irrelevante
aquí; los releases salen a decenas de adaptadores por semana, que es la firma
de la generación por plantilla, no de adaptadores probados. Licencia AGPL:
usarlo como proceso externo no contamina, forkearlo y servirlo sí.

Lo aprovechable es el motor: **definición JSON declarativa de una API (o una
especificación OpenAPI subida) → herramientas generadas en tiempo de
ejecución**, con modelado de la respuesta por campo. Serviría para que el
usuario conecte un servicio nuevo sin escribir código. Y tiene una carencia que
aquí ya está resuelta: no tienen recuperación de herramientas, así que con el
catálogo entero activado inundan el contexto del modelo. Combinar su generador
con la recuperación por lenguaje natural de OBJ-7 resuelve justo lo que ellos
no resuelven.

No se abre objetivo todavía: es una función de producto, no una mejora del
harness, y compite en prioridad con lo que ya está a medias.

## Descartado

### Catálogo de skills como «sistema operativo de harnesses»

Se anuncia con cifras de catálogo (cientos de skills, decenas de agentes y
comandos). No hay motor: son ficheros markdown con frontmatter más scripts de
instalación que los copian al formato de cada harness anfitrión. Toda la
ejecución la pone el anfitrión.

Dos señales decisivas: el recuento cambia entre el anuncio y el README actual
(catálogo que crece por generación, no por curación), y el propio repositorio
incorporó un validador de calidad porque estaban entrando skills «sin
estructura, demasiado vagas o con ejemplos tipo secreto», con un mínimo de
caracteres para bloquear entradas vacías. No hay ninguna medición de que usar
ese catálogo mejore nada.

### El harness auto-mejorable y su resultado insignia

Titular: 95,5 % en un banco de pruebas de razonamiento frente a un baseline
humano de 95,4 %, con el modelo solo en torno al 30 %. Se cae al mirarlo:

- El 30 % de partida no es una medición propia con el mismo protocolo: es una
  cifra ajena tomada de una leyenda de gráfica, mientras los autores admiten
  que sus propias repeticiones con ese montaje salieron peor y las
  descartaron. Compararon su mejor caso contra el peor caso ajeno.
- No publican tokens, intentos, tiempo ni coste, y las métricas clave no se
  definen formalmente. La replicación independiente es imposible por
  construcción.
- En las dos comparaciones donde sí corrieron cabeza a cabeza con condiciones
  idénticas, **empatan o pierden** contra el harness de referencia. El salto
  solo aparece en el banco de metodología menos controlada.
- Ese banco usa un conjunto público que sus propios creadores han desautorizado
  para comparaciones serias, por ser manipulable.
- Un margen de 0,1 % sobre el humano está dentro del ruido. Es un titular, no
  un resultado.

Se queda el patrón (OBJ-28), se descarta el proyecto.

### Grafo de conocimiento persistente por proyecto

Servidor MCP que mantiene un grafo de conceptos escritos por el propio modelo
(sin análisis estático), con SQLite local y embeddings en proceso. Proyecto
pequeño, honesto, sin cifras infladas — pero **Faustus ya tiene esto y con más
alcance** (FAUSTUS.md §154 y las quince fuentes del Context Engine, con
procedencia por ítem, que ellos no tienen).

Su punto débil es además instructivo: la calidad del grafo depende por completo
de que el agente se acuerde de consultarlo antes y actualizarlo después, sin
ningún mecanismo que lo verifique. Lo único copiable sería la búsqueda
semántica con embeddings locales sin clave de API, si la propia dependiera de
algo externo.

### Suite de agentes de seguridad ofensiva

Fuera de alcance. No se analiza ni se porta.

### Dos añadidos: un paquete de skills de negocio y una metodología de spec

Llegaron con el barrido ya cerrado. Ninguno aporta mecanismo.

El primero son unas veinte skills en markdown con el mismo frontmatter que las
de aquí, de dominio comercial (producto, marketing, redacción). El contenido no
es relleno generado — el generador de PRD que se revisó trae lista de
comprobación y criterios cuantificados — pero es contenido vertical, no una
capacidad de plataforma: equivale a añadir skills ya escritas, no a mejorar el
harness. Lo único con interés es su patrón de autoría: declarar supuestos y una
lista de auto-verificación *antes* de generar el artefacto.

El segundo es una CLI en Go, con CI y pruebas de verdad, que genera plantillas
de especificación para media docena de asistentes distintos. La metodología se
resume en una plantilla de siete secciones más unos comandos que se la pasan al
modelo por fases; no hay ningún mecanismo que valide que el código cumple la
especificación — su propia documentación no explica cómo funcionaría esa
comprobación. Resuelve la portabilidad entre asistentes, que aquí no es un
problema. Lo aprovechable: las siete dimensiones (requisitos, entidades,
enfoque, estructura, operaciones, normas, salvaguardas) como **plantilla de
nodo** del grafo de conceptos, para que una skill de diseño de función obligue
al modelo a declarar entidades, contratos y guardarraíles antes de tocar
código. Treinta líneas propias, no una dependencia nueva.

## Método

Cuatro sub-agentes en paralelo, uno por familia (memoria y contexto; decisión
tipada y navegador; harnesses auto-mejorables; conectores), con el encargo
explícito de desmontar cifras y distinguir mecanismo de eslogan. El cruce
contra las capacidades actuales se hizo después, no antes, para no sesgar el
análisis hacia «ya lo tenemos».
