# Announced deprecations (OPS-06)

Source of truth: `src.api_version.DEPRECATIONS`. This file is generated by
hand to match it today (no build step exists to render it automatically) —
if the two ever disagree, the module wins and this file is stale.

Each entry, when one exists, carries: the affected `route`, the version it
was announced `since`, the `sunset` date after which the old shape may stop
being served, and a `replacement` (a route or field to migrate to), or
`null` when the feature is being retired outright.

## Active deprecations

_None yet._ This lot introduces the registry (`api_version.DEPRECATIONS`,
`api_version.deprecation_headers()`) with nothing scheduled for removal —
COMUN rule 3 (no capability is ever lost) means nothing existing is being
deprecated as part of this lot. A future change that needs to retire a wire
shape appends an entry here and to `DEPRECATIONS`, and calls
`api_version.deprecation_headers(route)` from that route to attach
`Deprecation`/`Sunset`/`Link` headers (RFC 8594) to responses — additive
headers only, so an unaware client keeps working exactly as before until
`sunset` actually arrives.

## Process for a future breaking change

1. Add the field/route's replacement first; ship both old and new shapes
   together for at least one lot.
2. Append an entry to `api_version.DEPRECATIONS` naming the old shape, the
   replacement, and a `sunset` date far enough out that an integrator has
   time to move.
3. Wire `api_version.deprecation_headers(route)` into the affected route's
   response headers.
4. Only after `sunset`, and only in a change that also raises
   `MIN_CLIENT_VERSION` if the removal is one an old client cannot safely
   ignore, remove the old shape.
