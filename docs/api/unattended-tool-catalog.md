# Unattended tool availability and native schemas

An unattended chat keeps its connected MCP tools available through the existing catalog and `lookup_tools`. It no longer loads every job MCP schema into every model request merely because the run is unattended. This separates tool availability from the schemas required by the current step; it does not change autonomy, permissions, input, output, or model settings.

`stream_agent_loop` accepts optional `catalog_tools`, appended to its existing parameters for positional compatibility. The chat route supplies the unattended MCP names there. `forced_tools` keeps its existing immediate-schema meaning for explicit web/browser choices, the originating Hoard's tools, project tools, delegation and teams. Named tools, retrieval selections, workspace floors, skill requirements and lookup promotions still receive their existing treatment.

With `agent_tool_catalog=true`, catalog-only names join the selected executable set after its hot selection has been established. A tool that is both selected for this step and in the catalog remains native. The existing compact catalog lists available names and tells the model to use `lookup_tools`; a query or exact-name lookup loads the returned permitted schemas for the next round. Those promotions remain native for subsequent rounds of the turn. A caller-pinned `relevant_tools` selection is not widened by unrelated catalog names. Existing disabled tools, connector policy, code-only exposure and dispatch rules continue to apply.

Older chats may have persisted all unattended MCP names as hot. Sticky selection now removes that inherited blanket schema exposure for catalog-only names before saving its cache, while preserving the current turn's selected hot names and executable union. It does not repeat the demotion between tool rounds, so it does not undo a lookup promotion.

When the catalog setting is disabled, or the chat uses its existing lean profile, supplied catalog names follow the previous forced-tool path. A call without `catalog_tools` keeps its previous behavior. The existing ALL-selection fallback remains ALL; this change does not turn an unknown selection into an MCP-only set or start any server to discover tools.

Verification uses the real unattended route branch, production agent loop, candidate request preparation, lookup handler, promotion and MCP dispatch against an in-memory manager with no service connections. Cases cover a large MCP catalog, current named/retrieved/forced overlap, an older persisted hot set, catalog disabled, caller-pinned scope, disabled lookup results, normal callers without the new argument, and preservation of a request over three million characters with `max_tokens=0`. These CPU checks do not establish the provider's real token count, native latency or model quality. Runtime QA must inspect the final prepared request and demonstrate discovery and execution with the configured provider.
