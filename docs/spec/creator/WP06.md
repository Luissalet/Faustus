# WP06 — Model identity vs. deployment (MOD-01, MOD-02, MOD-19)

## Qué hay

`src/model_identity.py` (nuevo) separa tres niveles, como pide
`docs/04_MODELOS_Y_RECURSOS.md`:

- **ModelSpec**: identidad de pesos (vendor, family, digest, parameter_size,
  quantization, license, modalidades, capabilities). `model_spec_id` es
  determinista por digest (`ollama:digest:<digest>`); sin digest cae a un
  hash de vendor+family+model_id.
- **DeploymentManifest**: identidad de ejecución (`engine{kind,version}`,
  `endpoint_id/url`, `configuration` efectiva, `configuration_fingerprint`,
  `availability`). `deployment_id = sha256(engine_kind|engine_version|
  model_digest|configuration_fingerprint)` — exactamente la fórmula de la
  ficha; el endpoint NO entra en el hash (misma config + mismo digest +
  mismo engine = mismo deployment, venga de donde venga).
- **CapabilityEvidence**: `declared|inferred|probed|measured`, fuente,
  fecha, condiciones, método. `ModelIdentityStore.resolve_capability`
  aplica el orden measured > probed > inferred > declared, manteniendo
  TODAS las entradas (`list_evidence`), nunca descartando la más débil.

`resolve_deployment(endpoint_url, model)` usa
`src/model_capability_readers/ollama.py` para normalizar `/api/show` (ya
existente, sin reinventar el parseo) y dos funciones de red aisladas,
`_fetch_tags`/`_fetch_show`/`_fetch_version`, monkeypatcheadas en todos los
tests — cero red real en la suite.

Persistencia: `DATA_DIR/creator/model_identity.db` (sqlite, patrón de
`src/harness_evolution/store.py`: conexión por llamada, WAL, sin CAS
transaccional porque `deployment_id`/`model_spec_id` son funciones puras de
sus entradas — dos escritores calculan la misma fila).

`src/model_calibration.py::save_tested` gana un parámetro opcional
`deployment_id=None`, puramente aditivo: la clave legacy
`ollama|digest:<digest>` y su lectura no cambian en absoluto (test propio lo
verifica byte a byte). Cuando se pasa `deployment_id`, cada capacidad recién
probada se registra también como evidencia `probed` bajo ese deployment.
Cuando NO se pasa (todo caller anterior a este lote), se registra como
`inferred` bajo un `legacy_deployment_id(key)` (`legacy_unknown:<hash>`) —
MOD-19 "migrar probes viejos a scope legacy_unknown" — nunca promovido a
`probed`/`measured`. Todo el bloque está tras `creator_enabled` (default
`False`, `src/settings.py`): con el flag apagado no se lee ni escribe nada
en `model_identity.db`.

`routes/model_identity_routes.py` (nuevo): `GET /api/models/identity`
(resuelve, persiste spec+deployment, no carga el modelo), `GET
/api/models/deployments` (los conocidos + conteo de evidencia), `POST
/api/models/deployments/{id}/evidence` (admin, evidencia manual/medida).
Las tres responden 404 con `creator_enabled=False`, comprobado antes de
tocar el store.

## Rutas y flag

`creator_enabled` (default `False`). Wiring de `app.py` pendiente — ver
`WP06_wiring.md` (dos líneas, mismo patrón que `budget_routes.py`).

## Migración/rollback

Sin migración destructiva: el store nuevo es un fichero sqlite adicional;
borrarlo no afecta `model_capabilities.json` (autoridad legacy intacta).
Apagar `creator_enabled` detiene toda escritura nueva sin perder lo ya
guardado. Ningún dato existente se reinterpreta.
