## Qué hay

`tests/creator_harness/` (paquete nuevo):

- **`fixtures.py`**: generadores deterministas. `png_bytes()`/`jpeg_bytes()`
  con PIL (cuadrantes de color conocidos); `corrupt_png_bytes()` (IDAT real
  corrompido, cabecera intacta — no un heurístico de tamaño);
  `truncated_bytes()`; `wav_bytes()`/`silence_wav_bytes()`/
  `overlapping_voices_wav_bytes()` con `wave`+`math.sin` puro, sin librería
  de audio; `make_mp4()`/`make_vfr_mp4()` vía `ffmpeg`/lavfi
  (`testsrc`/`sine`/`testsrc2` con drop de frames para VFR),
  `ffmpeg_available()`/`ffprobe_available()` cacheados con
  `functools.lru_cache`. `conftest.py` cachea el MP4 por sesión
  (`tmp_path_factory`, `scope="session"`) y hace `pytest.skip` explícito si
  no hay `ffmpeg` — nunca un fixture vacío silencioso.
- **`fake_engines.py`**: `FakeAdapter`, un `AdapterPort` completo cuyo
  comportamiento lo decide `scenario` (`SCENARIOS`, 11 valores: success,
  timeout, corrupt/truncated output, cancel tardío, cancel-vs-completion,
  motor caído a mitad, disco lleno, respuesta lenta, submit perdido,
  rechazo antes de cola). `describe().engine == "fake"` siempre — un test
  verde aquí nunca puede leerse como evidencia de un motor real. `disk_full`
  es un context manager que sustituye `builtins.open`/`shutil.disk_usage`
  solo durante el bloque (siempre restaurado, incluso en excepción).
- **`matrix.py`**: las 12 filas de la matriz mínima de
  `08_PRUEBAS_Y_ACEPTACION.md`, con `owner="wp36"` (las que este paquete
  prueba) u `owner="other_wp"` (documentadas, no fingidas aquí: Autorización
  → WP09, Artefactos/Edición → WP02/WP03, Contexto → WP27, Local-only →
  WP32, Import → WP04). `registered_adapters()` reusa
  `src.creator.adapters.registry()` (pkgutil) sin lista paralela.
- **`test_adapter_contract.py`**: contrato genérico contra TODO adapter que
  `registry()` encuentra (hoy `comfyui`, `ffmpeg`), no casos especiales por
  adaptador: `describe()` nunca crea job; `plan()` puro (sin efecto
  observable, rechaza basura sin excepción); `submit()` de un plan inválido
  → `rejected_before_queue` sin job; `collect()`/`cancel()` de un job
  desconocido → nunca `ok`/`valid`, enum documentado; `reconcile()` cae a
  `status()` cuando el manifest declara `supports_reconcile=False`.
  `test_every_registered_adapter_has_a_contract_setup` falla si aparece un
  adaptador nuevo sin cobertura, en vez de saltarlo en silencio.
- **`test_failure_matrix.py`**: las 7 filas `owner="wp36"` con
  `fake_scenario` probadas con `FakeAdapter` — submit perdido → estado
  incierto; motor caído → `unknown` nunca resucita a `completed`; cancel
  simultáneo con completar → transición canónica única; cancel tardío →
  `too_late`; disco lleno/salida corrupta/truncada → `collect()` nunca
  registra. Dos tests de bookkeeping impiden que una fila nueva quede sin
  prueba o un escenario sin fila.
- **`test_resources_under_failure.py`**: fila "Recursos" contra
  `src/creator/resources.py` real (mismo patrón que
  `tests/test_creator_resources.py`): dos endpoints con el mismo device id
  comparten un slot serial; modo `measured` con dispositivo sin lectura cae
  a serial; `release()` libera tras fallo/cancel/caída de worker
  (parametrizado); doble `release()` no sobre-libera; `release()` de un run
  nunca admitido es no-op.
- **`scripts/creator_adapter_harness.py`**: corre la matriz `owner="wp36"`
  contra `FakeAdapter` y, si hay `ffmpeg`/`ffprobe` reales, un trim real +
  truncado real de su propia salida (`collect_truncated_output` a nivel
  `real_engine`); escribe `DATA_DIR/creator/harness/<run_id>.jsonl` con
  `evidence` (`fixture|fake_engine|real_engine`) y `contract_ok` por celda;
  sale con código 1 si alguna celda incumple el contrato documentado.

## Hallazgo (no corregido — CONTRATO.md: "NO arregles adaptadores")

`FfmpegAdapter.collect()` deja propagar `OSError` (p. ej. disco lleno) en
vez de devolver `CollectResult(ok=False)` — mismo patrón real en
`ffmpeg.py::collect()` (`shutil.copyfile`/`open` sin `try/except`).
`test_collect_disk_full_fails_without_announcing_completed` documenta esto
con `pytest.raises(OSError)` explícito, no un `xfail`: es comportamiento
REAL y probado, anotado para quien decida si `collect()` debe degradar a
`CollectResult` en vez de propagar.
