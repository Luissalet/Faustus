# WP32 — Lifecycle de plugins seguro

## Qué hay

`src/creator/plugins.py`: un único ciclo de vida para los cuatro tipos de
"plugin" del Creator — adaptador de motor (`engine_adapter`), servidor MCP de
medios (`mcp_media_server`), skill de producción (`skill`), receta ComfyUI
(`comfyui_recipe`):

```
discover -> inspect -> verify -> install -> enable/disable -> update -> rollback -> uninstall
```

- **`discover(owner, sources)`** solo registra fuentes declaradas en el
  catálogo (`creator_plugin_sources`); nunca hace fetch ni ejecuta nada
  (EXT01: pegar una URL desconocida no instala nada).
- **`inspect(source)`** trae el paquete a un directorio de staging efímero y
  construye un `PluginManifest` (id/version/digest/kind/capabilities/
  permissions/license) leyendo `plugin.json`, o — para skills sin
  `plugin.json` — el frontmatter de `SKILL.md` vía
  `src.skills_runtime.bridge.permissions_from_frontmatter` (reuso literal, no
  reinterpretación).
- **`verify(manifest, requires, privilege_hits)`** rechaza: forma inválida,
  claves de frontmatter privilegiadas (`skill_import_review.PRIVILEGE_REQUEST_KEYS`),
  o cualquier permiso (`network`/`fs`/`gpu`/`cost`) que el paquete parezca
  necesitar (por `requires` propio o backends de skill) sin declararlo.
- **`install`** siempre re-hace staging+verify (nunca confía en el catálogo
  `discover`); solo entonces escribe. Para `skill`+`git` delega la
  colocación/pin en `src.skill_sources.install` (ADP-25) — mismo digest, sin
  autoridad paralela. El estado de licencia queda SIEMPRE en `unreviewed` al
  instalar, sin importar lo que el propio `plugin.json` afirme.
- **`enable`/`disable`**: `enabled` persistido, revalidado en `check_use()`
  en cada uso. `enable` nunca abre ni toca `approval_store` — solo ensancha
  el techo de permisos (`permission_policy`), el permiso real sigue yendo
  por aprobación por tarea (ADR-14). `enable` se rechaza si
  `license_review_status == reviewed_blocked`.
- **`update`**: misma puerta que `install`; hace backup byte-a-byte del
  directorio actual antes de sustituir, resetea la revisión de licencia a
  `unreviewed` y deja el plugin deshabilitado (contenido nuevo exige
  re-habilitar explícitamente).
- **`rollback`**: restaura el backup verificando el digest antes y después
  de escribir — nunca confía en la copia ni en la escritura.
- **`uninstall`**: marca `uninstalled`+`enabled=False`, conserva ficheros
  `retention_days` (30 por defecto); `purge_expired()` es el paso explícito
  de borrado, nunca implícito.
- **`verify_installed`**: recalcula el digest en disco y lo compara con el
  registrado; si difiere, deshabilita el plugin y registra el evento
  `digest_mismatch` con `trace`.
- **`permission_policy`/`check_use`**: la interfaz que `tool_capabilities`/
  `preflight` deberían consultar — techo, nunca concesión.

## Store

sqlite `DATA_DIR/creator/plugins.db`: `creator_plugins` (proyección por
`(owner, plugin_id)`), `creator_plugin_sources` (catálogo declarado),
`creator_plugin_events` (histórico append-only, `trace` por mutación).
Abrir/cerrar conexión por llamada, WAL, `BEGIN IMMEDIATE` en escrituras. Los
directorios de instalación viven bajo `DATA_DIR/creator/plugins/<owner
hash>/<plugin id hash>/{current,previous}` — aislados por propietario;
`env`/secretos por plugin también están aislados por owner y nunca entran en
`creator_plugin_events`.

## Rutas

`routes/creator_plugin_routes.py`, prefijo `/api/creator/plugins`: `GET ""`,
`GET /{id}/manifest`, `POST /install`, `POST /{id}/{enable|disable|update|
rollback|uninstall}`. Gate `creator_enabled` (404 con el flag apagado, antes
de tocar el store) + admin (`owner_is_admin_or_single_user`). Owner siempre
de la sesión, nunca del body. Montado en `app.py` tras WP30.

## Migración / rollback de este WP

Aditivo puro: fichero nuevo, tabla nueva, ruta nueva tras la última existente.
Apagar `creator_enabled` (ya default `False`) deja todo el módulo inerte;
borrar `DATA_DIR/creator/plugins.db` y `DATA_DIR/creator/plugins/` es
reversible sin tocar ninguna otra autoridad (skill_sources, mcp_manager,
etc. no se han modificado).

## Pendiente / gaps honestos

- `mcp_media_server` es solo metadato de ciclo de vida aquí; NO arranca ni
  registra el servidor en `src.mcp_manager` — eso queda para el WP que
  cablee ese punto (documentado, no integrado).
- Para `skill`+`git`, `install`/`update` clonan dos veces (staging propio
  para verify + el clone interno de `skill_sources`) — correcto pero no el
  más eficiente; optimización futura de un solo fetch.
- `permission_policy`/`check_use` están listos para que `tool_capabilities`/
  `preflight` los llamen, pero esos ficheros no se tocan en este lote (fuera
  de propiedad de ficheros de WP32).
