# WP16 — Subtitle editor

Status: implemented on top of WP12 (typed ops)/WP13 (timeline retiming)/WP15
(ASR transcript). New document kind `subtitles`, one document per caption
TRACK (one language) — switching tracks never touches the others.

## What exists

* `src/creator/subtitles.py` — pure functions: `from_transcript` (word-level
  timing when available, char-proportional fallback otherwise; packs words
  into cues respecting a per-language `SubtitleProfile`'s max chars/line,
  max lines (2 by default, never forced to 1), max CPS, min/max duration; a
  speaker change or a pause ≥ `pause_break_seconds` forces a cue boundary;
  no word is ever split), `regenerate_from_transcript` (re-segments fresh
  but keeps every `edited: true` cue verbatim over the fresh cues it
  overlaps — a human edit always outlives a later transcript pass),
  `qa_report` (`{actual, target}` per violated rule, never a bare
  pass/fail), `apply_retiming` (maps cue ticks through a
  `src.creator.timeline.retiming.RetimingMap`; a cue in an unmappable zone
  is marked `unmapped: true` and KEPT, never dropped), `to_srt`/`to_vtt`/
  `to_ass`/`export` (own exporters — a subtitle cue is a list of lines,
  which `src/media_subtitles.py`'s single-line `_clean_text` would collapse;
  ASS escapes every literal `{`/`}` so a malicious cue can never smuggle an
  override tag), `ffmpeg_burn_filter` (escaped `-vf subtitles=...` fragment
  for WP14's renderer to consume later — no dependency on that module here).
* `src/creator/ops/subtitle_ops.py` — `subtitles.edit_cue`, `.split_cue`,
  `.merge_cues`, `.shift_cues`, `.set_style`, `.apply_retiming`,
  `.regenerate_from_transcript`, auto-discovered by the WP12 ops registry
  and applied through the existing `POST /api/creator/documents/{id}/commands`
  route — no bespoke edit endpoint. Overlapping cues are legal (dual-track
  captions); only `transcript_ops.py` enforces non-overlap, deliberately.
* `src/creator/documents.py` — additive `subtitles` document kind + its
  structural validator (`_validate_subtitles`). `documents.DOCUMENT_KINDS`
  now includes it.
* `routes/creator_subtitle_routes.py` — `POST /api/creator/subtitles/
  from-transcript`, `GET .../{doc_id}/qa`, `GET .../{doc_id}/export?format=
  srt|vtt|ass`. Gated by `creator_enabled`; owner-scoped; a foreign/
  wrong-kind document answers 404 same as missing.
* Studio: `studio/src/screens/creator/Subtitles.tsx` (top-level "Subtitles"
  tab in `CreatorScreen.tsx`) + `studio/src/adapters/creator_subtitles.ts`.
  Cue list with inline-editable text, time range, speaker, per-cue QA
  warnings, Up/Down keyboard navigation, Undo/Redo (via WP13's generic
  `undoTo`), "Regenerate from transcript", SRT/VTT/ASS download.

## Flag

`creator_enabled` (existing, `src/settings.py`, default `False`). No new
subsystem flag — subtitles share the parent flag like every other
`creator_*` route.

## Migration / rollback

Purely additive: a new document `kind`, a new ops module, a new routes
module, one `app.include_router` line, one Studio tab. Disabling
`creator_enabled` hides everything (404s), same as every other Creator
package. No existing table/schema changed; `subtitles` documents live in
the same `creator_documents`/`creator_document_revisions`/
`creator_document_commands` tables WP02 already created. Rollback = revert
this lot's commit(s); nothing else depends on the `subtitles` kind existing.

## Known limitations / pending

* No real diarization/alignment beyond what WP15's transcript already
  provides — segmentation quality is bounded by that transcript's own
  timing precision.
* ASS rendering fidelity (fonts actually present on the machine, karaoke
  per-word highlight) is not verified against a real renderer — WP14's
  renderer is the integration point `ffmpeg_burn_filter` exists for.
* No waveform audio rendering in the Studio tab (text+timeline only) —
  SUB05's "vista waveform-texto" ships the text/timeline half; a waveform
  strip is a follow-up, not faked here.
