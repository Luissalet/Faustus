# H12 - Repairing the prompt neither deletes nor invents effects

## Acceptance criterion

Repairing the prompt must neither delete nor invent effects. A call that has no
response never disappears from the causal history; it is projected as an explicit
"no result / unknown" item. There is one projection function per protocol that every
renderer uses, repairs operate on a canonical history and leave a receipt each, and the
new projection was compared with the previous one on fixtures before becoming the
default.

## What was already there

* `src/llm_core.py::_sanitize_llm_messages` repaired tool pairs for OpenAI-style chat by
  pruning: a call with no result was deleted, a result that was not directly after its
  call was dropped as an orphan, a call without an id was deleted.
* `_build_anthropic_payload` and `_build_ollama_payload` each carried their own copy of
  that logic.
* `src/context_compactor.py::_sanitize_tool_messages` had a third copy.
* Nothing recorded what a repair changed.

## What was added

`src/history_projection.py` (new), the only place history is repaired.

* Canonical form: `CanonicalHistory` of `Plain`, `Exchange` (an assistant turn with its
  `CanonicalCall`s and their matched `CanonicalResult`s) and `Orphan` entries. Calls keep
  their real ids; results carry effect certainty from the private `_effect_status` key
  that `src/agent_loop.py::_append_tool_results` now stamps from the tool result's
  `status`; image and multimodal parts are kept as blocks.
* `build_canonical` and `_canonicalize` match results to calls inside the window up to
  the next assistant turn, then attach a late result to the nearest earlier unanswered
  call with the same id.
* One renderer per protocol: `render_openai_chat` (with `_merge_adjacent_users` for
  strict-alternation providers), `render_anthropic`, `render_ollama`,
  `render_text_fence` (calls as fenced blocks in assistant text, results as one
  untrusted-context user message, metadata stripped). `repair_tool_pairs` serves the
  compactor. `project(messages, protocol)` is the entry point.
* Receipts: each `Repair` has a stable `kind` (`unknown_result_added`,
  `call_id_assigned`, `result_moved_next_to_call`, `orphan_result_not_projected`,
  `duplicate_result_not_projected`, `malformed_call_not_projected`,
  `legacy_marker_rewritten`, `message_omitted`, `user_messages_merged`,
  `boundary_inserted`, `shadow_difference`), a reason, the call id, the tool and a
  detail that carries digests and never bodies. `recent_receipts` and `receipt_counts`
  expose a bounded in-process log.
* Wiring: `src/llm_core.py` (`_sanitize_llm_messages`, `_anthropic_messages`,
  `_ollama_messages`, `_history_protocol`) and `src/context_compactor.py`
  (`_sanitize_tool_messages`) call the projector. The previous code is kept as
  `_sanitize_llm_messages_legacy`, `_anthropic_messages_legacy` and
  `_sanitize_tool_messages_legacy`.
* Setting `llm_projection_mode` (`src/settings.py`, `src/agent_settings_schema.py`):
  `canonical` (default), `legacy` (rollback to the previous code) and `shadow` (send the
  legacy result, record every difference as a `shadow_difference` receipt).
  `llm_fence_history_without_tools` (default off) renders earlier native calls as fenced
  text when a request carries no tool schemas.
* MCP: the `harness` built-in server tool `history_projection` shows the repairs a
  message list would get, for any protocol, without touching the running app's log.

### Intended differences from the previous repair

1. An unanswered call is kept and answered with `UNKNOWN_RESULT_TEXT` (it was deleted).
2. A result separated from its call by other messages, or arriving after a later
   assistant turn, is re-attached to its call (it was dropped as an orphan).
3. A call without an id gets a synthetic `faustus_noid_*` id and an unknown result (it
   was deleted).
4. Compactor variant: a call whose result was trimmed gets `OMITTED_RESULT_TEXT`.

Every other generated history projects identically, and projection is idempotent.

## Evidence

The parity tests run the previous code and the projector over generated histories and
compare; every difference is one of the four above and has a receipt. The MCP tool was
also exercised through a real stdio client (an unanswered call comes back as
`user, assistant, tool` with one `unknown_result_added` receipt).

## Remaining limits

* Orphan results (no call anywhere before them) are not projected; they are receipted
  with a digest. Nothing is invented for them.
* The receipt log is per process; the MCP tool computes from the messages it is given
  and cannot read the running app's log.
* `llm_fence_history_without_tools` needs a check against a real model without native
  tools (the text-fence renderer is covered by unit tests only). The Windows check is in
  `H24.md`.
* `shadow` mode doubles the repair work on each request; it is meant for a short
  observation window.
