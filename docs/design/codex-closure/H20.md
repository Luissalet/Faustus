# H20: memory consolidation under leases, only when there is new work

## Acceptance criterion

No duplicated consolidation and no scope contamination: concurrent workers do
not each start the same tidy-up, a worker that stalled past its deadline cannot
publish after its successor, and a tidy-up whose input did not change ends
without calling a model.

## Already there

- `src/memory_curator.py` serialised curations inside one process with a lock,
  and ownership, scope and validity rules kept owners and projects apart.
- The legacy tidy-up (`src/builtin_actions.py::action_consolidate_memory`, run
  by the scheduler every few added memories) read the memory file, asked a
  model, and saved the list it had read at the start.

## Added

- `src/work_lease.py` (new): exclusive claims in a private SQLite file, shared
  by every process that uses the data folder.
  - `acquire` never blocks; a busy scope answers `LeaseDenied` (`held` or
    `backoff`). Every grant carries a fence that only grows for the scope.
  - `commit_window` holds the write lock while the holder publishes and says
    `ok=False` when a newer lease exists; a successor cannot be granted while a
    holder is publishing.
  - `release` records a watermark (input revision and algorithm version) only on
    success and only for the current lease; a failure schedules a retry with
    exponential backoff (`backoff=False` for cheap deterministic work).
  - `renew`, `is_current`, `is_unchanged`, `watermark`, `status`.
- `src/memory_consolidation.py` (new): fingerprint of the entries that matter
  (id, text, category, source, pinned; never the use counter), a claim per
  owner, a plan that is the difference between the start state and the decided
  state, and a commit that applies the plan to a fresh read inside the commit
  window: an entry edited since the first read is skipped, one added since is
  kept, a lost lease publishes nothing, the watermark covers only the ids the
  run saw.
- `action_consolidate_memory`: skips when the watermark matches (no model call),
  claims the owner's scope, commits through the plan, releases in `finally`,
  reports what reached the file. A broken lease store logs and lets the tidy-up
  run single-shot (the commit still reloads fresh data).
- `memory_curator.curate`: claims `memory-curate:<owner>:<project>` on top of the
  process lock; answers `{"skipped": "held"|"backoff"|"lease_lost"|"no_new_work"}`;
  checks the fence between passes and every 25 items; `skip_if_unchanged`
  (opt-in) ends early when the last successful pass saw the same items on the
  same UTC day.
- Read surfaces: `GET /api/memory-engine/jobs`; MCP tool `memory_jobs`
  (workers server).

## Limits

- The curator writes to the learned-memory database, a different file from the
  lease store, so its fence is checked between passes and every 25 items, not
  atomically with each write. A stalled curator can finish the item it is on.
  The passes are idempotent, so the outcome is a repeated pass, not corruption.
- `skip_if_unchanged` compares the state after the pass; a write by another
  party during the pass counts as seen.
- The legacy tidy-up file is still written by other code paths (adding and
  deleting memories) from their own reads; the commit protects against stale
  overwrites by the tidy-up, not between those other writers.
- The watermark treats any change to id, text, category, source or pinned as
  new work, so one added memory makes the next tidy-up consider the whole
  owner's group again.
