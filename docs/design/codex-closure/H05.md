# H05 - one authority for catalogue, schema and handler

## Acceptance criterion
The catalogue, the emitted schema and the handler of a core tool come from one
authority. A descriptor carries spec, handler, effects (including the ones that
depend on the arguments), resources, limits and exposure. Emitted schemas are
generated from it, dispatch resolves through it, current ids stay valid as
aliases, a parity test compares the emitted schema with the parser contract and
the declared limits with the applied limits, and MCP dynamic tools get a
descriptor built at discovery.

## What already existed
`src/tool_registry.py` (read-only catalogue snapshot over `FUNCTION_TOOL_SCHEMAS`
and `BUILTIN_TOOL_DESCRIPTIONS`), `src/tool_capabilities.py` (the only table of
effects, including `capabilities_for_action`), `src/tool_schema_receipts.py`
(definition hashes), `src/tool_schemas.py` (hand-written schemas and the native
argument parser, which had drifted from the schemas: `write_file` and
`apply_patch` advertised `base_revision` and `confirm_risky` that the parser
dropped).

## What was added
- `src/tool_authority.py`: `RegisteredTool`, `ToolLimits` (`LimitRef` resolves
  lazily to the constant the handler applies), `ToolEffects` (reads through
  `tool_capabilities`, per call via `capabilities_for_action`), `ToolResources`
  (path claims), `Exposure`, `ParserContract`, `ToolAuthority` (register,
  resolve by wire name / canonical id / alias, `handler`, `exposure_map`,
  `parity_report`), `descriptor_from_mcp` (descriptor built from a discovered MCP
  definition; not added to the process registry).
- `src/tool_authority_specs.py`: 17 authored tools and the PDF trio adopted as
  `contract` tools, with their schemas, parser contract, limits and aliases.
  `CODENAV_MAX_HITS` and `CODENAV_MAX_LINE_CHARS` are now constants the
  handlers apply and the descriptors declare.
- `src/tool_authority_schemas.py`: emits fresh schema objects, byte-identical
  to the previous hand-written ones (property order preserved).
- `src/tool_authority_catalog.py`: every other built-in tool is registered as
  `wrapped` (descriptor read from the catalogue that still owns its spec), so
  the registry covers 225 tools (17 authored, 3 contract, 205 wrapped).
- `src/tool_schemas.py`: authored families call `_emit_schema(...)`;
  `src/agent_tools/filesystem_tools.py`: limits read from the authority;
  `src/tool_security.py`: revocation covers canonical ids and aliases;
  `src/tool_capabilities.py`: `image_job` registered (effects) - it was missing
  on master; `src/tool_index_examples.py`: `image_job` examples - same.
- `routes/tool_registry_routes.py`: `GET /api/tools/authority`,
  `/api/tools/authority/{name}`, `/api/tools/authority/parity` (admin, read-only).

## Evidence
`write_file` with a stale `base_revision` is now refused through the native path
(before: the argument was silently dropped). The parity report is empty for the
shipped registry. `GET /api/tools/authority/parity` returns `ok: true`.

## Remaining limits
- 205 tools are `wrapped`: they have canonical id, limits/resources/exposure
  and effects from the authority, but their schema and parser are still owned
  by `src/tool_schemas.py`; the parity test does not assert an encoder for them.
  Migrating a family means moving its spec to `tool_authority_specs.py`.
- MCP descriptors are built per discovered tool when a step is captured (see
  H06) and are not stored in the process registry, so the admin route lists core
  tools only.
- Not exposed as an MCP server: the authority is an admin HTTP surface; a
  built-in MCP server would change the built-in server catalogue other work
  depends on.
