# H19 — no fictitious delivery and no hidden orphan workers

**Status: closed with limits.**

## Acceptance criterion

Queued steering messages are re-delivered or explicitly dropped with a reason after a
restart. Workers whose parent run is gone are listed and can be killed. Nothing
claims delivery without a receipt.

## What was already there

`POST /api/chat/steer/{session_id}` returned `{ok: true}` once a message was in an
in-memory queue. A "send after" message was announced as "it will be sent once this
turn finishes" but nothing sent it. A worker whose parent run ended kept running.

## What was added

- `src/steering_journal.py`: a receipt per message, folded from ledger `steer_*`
  rows. States `queued` -> `drained` -> `applied`, or `dropped` (with a reason, text
  kept) -> `redelivered`; `handed_off` for send-after. `applied` is written only by the
  place that did the thing: the loop's `steer` event (observed in
  `agent_runs._publish`) or the client's acknowledgement. `recover_after_restart()`
  drops everything the old process left unresolved. `carry_block()` puts dropped,
  unread messages in front of the model on the next turn, once.
- `src/agent_runs.py`: receipts on queue / drain; unread messages dropped with a
  reason when a run ends (`_drop_unread_steers`).
- `routes/chat_routes.py`: the steer answer carries `receipt`; new
  `GET /api/chat/steer/{id}/receipts`, `POST /api/chat/steer/{id}/claim`,
  `POST /api/chat/steer/receipt/{id}/ack`. `routes/chat_helpers.py`
  (`_carry_steering`) builds the next turn's note.
- Studio (`Studio.tsx`, `adapters/runReport.ts`): when a turn ends the client claims
  the held send-after messages, sends them as one new turn and only then
  acknowledges them.
- `src/orphan_workers.py`: `scan()` lists delegated workers whose parent run is
  `finished`, `replaced` or `gone` (after a grace period) and dispatch jobs whose
  record says live but have no task; `kill()` stops only a listed orphan.
  `GET /api/agent/orphans`, `POST /api/agent/orphans/{key}/kill`,
  `run_report view=orphans`.

## Evidence

Queue a "send after" message during a turn: the answer has a receipt in `queued`;
after the turn ends the next turn starts on its own and the receipt is `applied`.
Restart the server with one still queued: the receipt is `dropped`
(`process_restart_before_delivery`) and its text appears in the next turn's context.

## Remaining limits

- `redelivered` is recorded when the next turn's preface is built, which proves the
  text was put in the prompt, not that the model answered it.
- A send-after message is sent by the client; with no Studio window open the message
  waits (it is not lost: it is claimed on the next open, or dropped and carried after
  a restart).
- Orphan detection is by the parent run's state. Subprocess pids of external runners
  after a restart are not tracked.
