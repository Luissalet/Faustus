# H22: capability probes per protocol, declared vs probed vs unsupported

## Acceptance criterion

Separate what is declared, what was observed to work and what was observed not
to work, per endpoint, protocol and connection, and never let an observation
outlive the configuration it was made under.

## Already there

- Scoped calibration (`calibration_key`, `save_scoped_tested`,
  `get_effective_manifest` in `src/model_calibration.py`): observations keyed by
  vendor, endpoint id, protocol, model or digest and, in v3 keys, the endpoint's
  connection revision. Declarations and probes are stored apart; a skipped probe
  does not erase an earlier observation.
- `connection_revision` on model endpoints and `credential_revision` on provider
  credentials, rotated by ORM hooks (changes to the address, key, credential
  binding or kind; reconnecting an account).
- Probes existed only for the native Ollama API.

## Added

- **Revision triggers in the database** (`core/database.py`,
  `install_revision_triggers`, migration step `add_revision_triggers`, last in the
  formal sequence). The ORM hooks cannot see a plain SQL write (a script, a bulk
  `UPDATE`, another tool opening `app.db`), so the same rule now lives in SQLite:
  - an endpoint row inserted without a revision gets one;
  - changing `base_url`, `api_key`, `provider_auth_id` or `endpoint_kind` rotates
    `connection_revision` unless the same statement already did (so an ORM write
    rotates exactly once);
  - changing a credential row's provider, owner, address, mode or tokens rotates
    its `credential_revision` and the revision of every endpoint linked to it.
  Names, caches, enabled flags, timestamps and unchanged values do not rotate.
  The step is additive and idempotent, skips tables that do not exist, and keeps
  existing revisions.
- **Chat-completions probes** (`src/openai_probes.py`, new): tool calling,
  streaming tool calls (assembled from SSE deltas), JSON mode
  (`response_format`), vision (an `image_url` part) and effective context (only
  with a declared length). Three states, never collapsed:
  - `supported`: the server did it;
  - `unsupported`: HTTP 400/415/422 that names the feature, or an answer that
    shows it does not (text instead of a tool call, prose instead of JSON);
  - `unknown`: timeout, connection error, 401/403, 404, 429, 5xx, or a rejection
    that does not name the feature. Never turned into a pass or a fail.
  Results use the stored `tested` shape plus `evidence.state`, HTTP status and a
  reason; no header, key or long prompt is stored. A time budget marks the rest
  `unknown` (skipped), not missing.
- **Revisioned writer**: `probe_endpoint` resolves the endpoint once, captures its
  connection revision and protocol (`openai_chat_completions`, read from the
  resolved chat URL only; messages-style, Ollama native and subscription URLs are
  refused with 422) before the first request, and files the results under that
  revision. A change while probes are in flight files them under the old revision,
  where nothing current reads them. A later inconclusive attempt keeps the earlier
  observation and records only `last_attempt`.
- **Declared vs probed** (`model_calibration.capability_states`): one row per
  capability with `declared` (true/false/none), `probed` (true/false/none), a
  verdict (`verified`, `unsupported`, `declared_unverified`,
  `declared_unsupported`, `undetermined`, `not_declared`) and `conflict` when the
  observation contradicts the declaration. The declaration today is the
  endpoint's `supports_tools` setting.
- Surfaces:
  - routes `GET /api/model-probes/openai` (read, no network),
    `POST /api/model-probes/openai` and `POST /api/model-probes/openai/url`
    (admin and same-origin; the second probes a bare address and files nothing);
  - the generic `app_api` bridge cannot run a probe (blocklisted POST, with a
    message; the read stays open);
  - MCP tool `context_model_capabilities` (`read`, `probe`, `probe_url`);
  - scheduler action `probe_model_capabilities`;
  - `scripts/probe_openai_endpoint.py` for a server that is not registered;
  - Studio: Settings, Models, per endpoint "What it declares and what it does"
    (table of declared, observed and verdict per capability, model picker,
    "Check what it does" for admins, optional image check), Spanish and English.

## Limits

- Probes are short requests, not a benchmark. A `supported` means it worked on
  this request at this time; `unsupported` from an answer (not a named rejection)
  can be a bad sample from a model that can do it. The verdict keeps the reason.
- Only the `openai_chat_completions` protocol is probed. Messages-style endpoints,
  Ollama native (which has its own calibration) and subscription protocols are
  refused rather than guessed.
- Readers that choose a model at run time (chat loop, router) are not changed:
  they keep their existing behaviour; the new evidence is available to them and to
  people through the surfaces above.
- The triggers compare the stored `api_key` text, so any raw SQL that rewrites it
  (even re-encrypting the same key) rotates the revision and retires the probes:
  conservative by design. A raw `INSERT OR REPLACE` that supplies the same id and
  revision by hand is not detected.
- A trigger cannot tell a legitimate refresh from an external change when both
  arrive as one SQL statement that also sets the revision itself; such a writer
  takes responsibility for the revision.
- The effective-context probe needs a declared context length, which servers of this kind
  rarely state, so it is usually skipped.
