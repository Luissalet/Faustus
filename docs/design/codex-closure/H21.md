# H21: instructions per directory, skill versions, precedence and provenance you can see

## Acceptance criterion

Precedence and provenance are visible: for any file the agent works on, which
instruction files apply, in which order they win, where each one comes from
(path, hash, trust state, how it reaches the model) and which version of a skill
was disclosed at each level.

## Already there

- `src/project_instructions.py`: one root file (first existing candidate of
  AGENTS.md and the other configured candidate names) in the system prompt, gated by `src/workspace_trust.py`
  and rendered from one captured snapshot.
- `src/project_rules.py`: path-scoped rules delivered once per conversation with
  the tool result that touches a matching file.
- `src/skills_runtime/disclosure.py`: level 0 (index), 1 (bodies) and 2
  (references) with receipts (version, hash) for the level 1 bodies only.
- `src/context_engine/prompt_audit.py` already read `instruction_provenance` and
  `skill_disclosure` from message metadata, but nothing produced the first and
  only the level 1 part of the second.

## Added

- `src/instruction_hierarchy.py` (new), behind `agent_instruction_hierarchy`
  (off by default; with it off the prompt, digests and tool results are byte for
  byte what they were).
  - `scan_nested`: one instruction file per subdirectory (first existing
    candidate, same lookup order as the root), bounded by depth, directory and
    file counts, skipping vendored, hidden, empty and symlinked trees.
  - Precedence, stated once in the prompt index and in every delivery: what the
    user says first; then the file in the directory closest to the file being
    worked on; then the directories above it up to the root. Root side is shown
    first and the closest directory last.
  - Delivery: the system prompt keeps the root file and gains an index of the
    nested files (path, scope, size, short hash, never the text). The text of a
    nested file is appended to the result of the first read/edit/write/listing
    that touches its directory, once per conversation and file version
    (`path_note`, same mechanism as path-scoped rules, combined in
    `_path_rules_note`).
  - Trust: nested files are digest parts (`nested_parts`) of the same folder
    approval. A new or edited nested file turns an approved folder into
    `changed`, and nothing nested is shown, indexed or delivered until it is
    approved again. Everything is rendered from the bytes captured by one
    `instructions_snapshot`. The approval card lists them (`kind:
    nested_instruction`) and is no longer capped at 16 files when nested files
    are present. With trust mode `off` nothing is withheld and nested files are
    still delivered.
  - `provenance`: one row per file that can reach the model, ordered by
    precedence (path, source root/nested, scope, sha256, bytes, chars, truncated,
    trust, delivery). It rides on the system message as
    `metadata.instruction_provenance` (also through the merged-prompt path), so
    the prompt audit's instruction receipts now have a producer. Tool events
    that delivered a nested file carry `instruction_delivery` (rel, scope, hash).
  - `instructions_for(workspace, path)`: the chain for one path from a single
    snapshot; text only when approved, otherwise `withheld`.
- Skill versions at every level: the level 0 index text now carries its receipts
  (`DisclosedText`, a `str` subclass, so `_build_base_prompt` keeps its shape)
  and the skills message receipt lists index and body fragments together;
  `manage_skills view` (level 1) and `view_ref` (level 2) return a
  `skill_receipt` (skill, level, version, hash, relative file) that is persisted
  on the tool event and never echoed to the model.
- Surfaces: `GET /api/workspace-trust/instructions?workspace=&path=` (admin,
  read-only); MCP tool `context_instructions`; setting in the agent settings
  schema ("Instructions per directory").

## Limits

- Only the first existing candidate per directory counts, like the root; a
  directory with two candidate files uses the first in the configured order.
- The scan is bounded (depth 6, 2000 directories, 64 files). A tree beyond that
  is reported as limited by the scan and not all of it is covered.
- Delivery happens on file and directory tools (the same tools that trigger
  path-scoped rules). A shell command that reads a nested directory does not
  trigger it.
- With trust mode `off` the provenance lists the nested files but not the root
  file (that path keeps reading the root file on its own, unchanged).
- In trust mode `ask`, a folder that Faustus already has checkpoints for is
  approved automatically on first sight (existing behaviour); with the
  hierarchy on, nested files present at that moment are covered by that
  automatic approval.
- The skill receipts are assembly and read receipts, not proof that the model
  followed the skill.
