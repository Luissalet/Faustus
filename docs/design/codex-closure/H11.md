# H11 - Unified process API and cancellation

Acceptance: one lifecycle for process, stdin and output.

Status: CLOSED-WITH-LIMIT (limit: the Windows Job Object assignment of managed processes is written but was not run on Windows here).

## Already there
`bg_jobs` (background shell jobs with bounded logs), `process_ownership` (pid + creation-time proof, tree termination), persistent tasks, the Windows Job Object helper.

## Added
- `src/process_manager.py`: opaque handles. Each record holds owner, session, environment policy, route, the initial command, state (`starting`, `running`, `exited`, `stopped`, `timed_out`, `failed_to_start`, `orphaned`, `lost`, `uncertain`), exit code, termination reason and a bounded output ring with an absolute-offset cursor (reads report dropped bytes; cuts never split a UTF-8 character). Stderr is merged into the same stream. Reader and waiter threads are independent of the calling event loop, so closing the UI or cancelling a tool-call task does not kill a process; only `stop`, the runtime limit or a cancelled work scope do.
- Tools `process_start`, `process_read`, `process_write_stdin`, `process_stop`, `process_list` (builtin, MCP server `execution`, tool index, capabilities, plan-mode read-only for read and list). Stdin verifies session, owner and the current permission on every write, and stops when confinement became required. `process_stop` terminates only the handle's own process tree through `process_ownership.terminate_tree` (pid plus creation time); it never matches an application by name and never adopts a process.
- Persistence: a JSON store (`FAUSTUS_PROCESS_STORE` overrides the path), written atomically, holding metadata and only the output tail. After a restart a handle whose process is still alive with the same creation time is `orphaned` (read-only tail, no stdin), one that is gone is `lost` with `outcome_unknown`; nothing is ever re-spawned. A remote disconnect marks running remote handles `uncertain`.
- `bg_jobs` are listed, read and stopped through `bg:<id>` handles (adapter); `#!bg` results carry `process_handle`. `chat_routes` cancel with `scope=work` also cancels the session's managed processes.
- Under `required` confinement a host process start is refused (same `sandbox_exec` refusal), as is stdin to an existing host process.
- Settings: `agent_process_manager`, `agent_process_max_handles`, `agent_process_max_runtime_seconds`, `agent_process_buffer_bytes`. Routes `GET /api/process-handles`, `POST /api/process-handles/stop`.
- Fix in this round: a handle could be seen as finished before its final output total was persisted; the state check now happens under the store lock.

## Tests
`tests/test_process_manager.py` (30): output bounded with a gap-reporting cursor, lossless reads when keeping up, UTF-8 safe cuts, a silent process stays valid, closing the event loop and cancelling the tool task do not stop the process, stdin round trip and close, another owner or session is refused, permission re-checked on every write, required mode blocks start and stdin, handle limit, stop kills its own children, stop never touches an unrelated process with the same program, a recycled pid is not signalled, runtime limit reason, cancel for a session, orphaned and lost after a restart, remote disconnect is uncertain, bg job through its handle, Windows job closed before the tree kill (mocked), tools round trip, atomic store with only the tail. Neighbouring suites (bg jobs, process ownership, bounded output) pass.

## Limits
- The Job Object path for managed processes is covered by a mocked test only.
- Handles hold a tail, not the whole output: a finished handle's early output beyond the buffer is gone (reported as dropped bytes).
