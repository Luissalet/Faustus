## When to Use

A piece of professional work is starting or in progress: a request has arrived, there are meetings, documents and money questions, and you must turn that into a scope, a proposal, reviewed deliverables and a package you can hand over and reproduce later. This procedure does not set prices without the person's rates and does not store contact details or payments itself; it references them where other apps own them.

## Procedure

1. Read the app's tool list. Open or create the engagement file and record the request in the client's words, the date, the decision maker, the deadline and what success looks like. Link contacts, files and money items instead of copying them.
2. Write the scope as lists: in scope, out of scope, assumptions and dependencies on the client. Every vague word ("support", "optimise", "review") becomes a measurable item or moves to out of scope.
3. When the request changes, compare the new scope with the saved one rather than editing in place. Each difference becomes a change option with effort and cost, so the client chooses; unrecorded changes are the usual source of disputes.
4. Estimate effort as ranges with the reason for the width, not a single figure. Save the bands you use so later proposals stay consistent. Make the biggest uncertainty visible.
5. Draft the proposal from the scope. Tag each claim as fact from the file, assumption, or commitment. Run the check that blocks internal names and notes from the client-facing text, then read the draft as the client would, looking for anything that exposes internal reasoning.
6. Review each deliverable against the scope item it satisfies: complete, correct, in the agreed format. Record the finding per deliverable, with the evidence, and what must change before release.
7. Build the delivery package so it can be reproduced: list the exact inputs, versions, the steps that generate each output and the checks passed. Rebuild it once from the list to confirm that the same files come out.
8. Close with a history entry: what was delivered, what was left out and why, open items for the client.

## Pitfalls

- A scope that is a list of activities instead of outcomes.
- Absorbing a change silently because it looks small.
- One-point estimates that the client reads as promises.
- Proposal text copied from earlier work with another client's wording left in it.
- Copying contact or payment data into the file, creating a second source that goes stale.
- A package that works only on the machine that made it.

## Verification

- The scope has in-scope, out-of-scope and assumptions sections, and every deliverable maps to a scope item.
- Each change since the first scope appears as a recorded comparison with a chosen option.
- The proposal passed the internal-name check and every claim is tagged.
- A rebuild of the package from its list produced the same files.
